# FlyBox 项目开发记录

> 平台: STM32F1 + FreeRTOS + CAN 总线电机驱动器 × 5 + TOF8 测距传感器 × 2
> 核心代码: `flybox_action.c/h`、`motor.c/h`、`tof8.c/h`、`imu.c` (任务入口)
> 记录时间跨度: 2026-07 ~ 2026-08

---

## 一、任务概述

**目标**: 实现"飞箱"机构的取箱 / 放箱全自动化流程。机构包含:

| 设备号 | 电机 | 功能 |
|---|---|---|
| 1 | 传送带左 | 箱体输送 (与右轮同步) |
| 2 | 传送带右 | 箱体输送 |
| 3 | 钩爪 | 钩住 / 松开箱体 (旋转机构, ≈255° 全行程) |
| 4 | 钩爪旋转 | 钩爪正面 ↔ 侧面 (≈355° 全行程) |
| 5 | 钩爪传送带(皮带) | 钩爪前后移动 (>550mm 行程) |

传感器: TOF25 (正面, 箱体接近测距) 、TOF26 (侧面, 放箱侧测距)。

**完整任务链**:
1. 电机 SN 绑定与初始化
2. 轮径标定 (各机构减速比不同)
3. 力矩回零 (撞机械限位定义零点) + 力矩阈值标定
4. 单轴运动接口 (距离/角度/速度/加速度)
5. TOF 距离联动 (迭代逼近目标距离)
6. PickBox 六步取箱流程 (含判定重试)
7. PlaceBox 五步放箱流程 (含 TOF25 补偿)
8. 故障恢复 / 急停安全 (AbortAndSafe)
9. 全程诊断变量体系 (Watch 窗口定位问题)

## 二、实现思路

### 2.1 初始化与绑定
- 上电后电机会通过 `0x0312` 广播 7 字节 SN; 主控用硬编码 SN 表匹配后回 `0x0313` 分配设备号。
- 之后 `0x0316` 配置参数 → `0x0408` 配置轮径 (重复写 3 次) → `0x0413` 锁定。
- 诊断: `g_flybox_init_diag` (1=SN收集超时 2=SN匹配不足 3=配置失败), LED 闪 N 次指示。

### 2.2 轮径标定
- 各电机机构/减速比不同, 轮径必须分别标定: `修正轮径 = 当前轮径 × (实测距离 / 指令距离)`。
- 实测结果: 传送带 31.94mm、钩爪皮带 6.39mm。
- **特例**: 钩爪(3)/旋转(4) 是纯旋转机构, 轮径保持 25.55 不可改 —— mm/° 换算系数 (11.236 / 7.955) 是在该轮径下标定的, 改轮径会导致所有角度动作按比例偏差。

### 2.3 力矩回零 (核心难点)
没有原点开关, 采用 **撞机械限位 + 力矩检测** 定义零点:

```
低速(30mm/s)朝限位方向相对运动 (行程 > 全行程)
  → 10ms 轮询力矩, |torque| ≥ 阈值 连续 3 次 (30ms 消抖) → 判定到限位
  → 反方向回退 2mm (三级恢复)
  → 回退后力矩验证 (回落 < 阈值才允许)
  → 发 0x0A 把当前位置设为零点
```

设计要点:
- **3 电机并行搜索** (`FlyBox_HomeMotorsParallel`): 到限位后不发任何 CAN 命令, 只标记 `limitReached` (电机顶在限位上自然不动), 避免额外总线流量和保持力矩拉低电源。
- **低速搜索**: 150mm/s 实测会把驱动器撞进深度保护态 (见问题 5.4), 降至 30mm/s + 加速度 20mm/s²。
- **卡滞探测**: 力矩超阈时按 `motorMoved` 区分 —— `|mainPosition|` 从历史最大值减小过 = 真实撞限位; 从未移动 = 卡滞 (开机已在限位 / 卡错误侧 / 机械自锁), 进入脱困流程。
- **限位卡滞脱困** (4 级 FreeFromLimit): 正向 30mm → 反向 30mm → 摇摆 ±20/60/100mm → 电流限制 0xFF + 摇摆后恢复配置。成功判据 = 力矩回落持续 200ms < 阈值。脱困成功后重新搜索, `retryCount` 上限 2 次, 全失败 = failReason 9 (机械卡死, Unlock 释放电机便于人工掰开, 不置零)。
- **零点偏移换算**: 力矩回零零点 = 机械限位, 与旧上电零点不同。绝对定位自动换算 `新目标 = 旧目标 - 偏移`: 钩爪 +45°、旋转 -45°、皮带 0。

### 2.4 力矩阈值一键标定
阈值无法从协议推算 (单位未定义), 做了一键标定流程 `FlyBox_Debug_CalibrateTorque` (`imu.c` 中 `FLYBOX_TORQUE_CALIB_ENABLE=1` 开启):
- 每电机三步: 反向退 80mm 离开限位 → 正向空载 50mm 记 baseline → 正向全行程撞限位记 limitPeak。
- **阈值 = baseline + (limitPeak − baseline) / 2** (中点法)。
- 实测结果: 电机3 = 90 (24/148)、电机4 = 90 (27/145)、电机5 = 350 (41/654, 小轮径大力矩正常)。
- 标定模式下 `FlyBox_Init` 检测到阈值未配置直接跳过回零返回 HAL_OK, 不阻断标定。

### 2.5 TOF 距离联动 (迭代逼近)
`FlyBox_GripperBeltMoveUntilTof25` / `FlyBox_ConveyorRunUntilTof26`:
- 中值滤波 (5 次采样, 30ms 间隔) + IIR 滤波 → 迭代逼近目标距离, 收敛判定 ≤ 5mm。
- **无效分支顺序**: 传感器故障 → 重启重试 / 滤波器预热中 → 等待重测 / 真超量程 → 盲进 50mm 步进。
- **滤波器预热保护**: 无效帧会重置滤波器, 从 0 爬升期间输出假近值 → 预热期 (validCount < 5) 发布无效值, `TOF8_IsWarmingUp()` 让上层等待而非盲进。
- 钩爪带总前进上限 500mm (防相对定位累积超限), 超限 → 皮带回零 → 重试。

### 2.6 PickBox 六步流程
```
入口安全前置: 松开 + 钩爪转正 (防上次中断遗留状态)
Step1: 钩爪带前进靠近箱体 (TOF25 联动至 95mm)
Step2: 钩爪钩住 (绝对 -90° 换算后坐标)
Step3: 三电机同步 — 钩爪带绝对回零 + 传送带左右相对前进
Step3.5: TOF25 判定箱体是否上带 (≤150mm=成功) ── 重试点A: 失败→松爪→回Step1
Step4: 松开钩爪 (旋转前必须松)
Step5+6: 旋转90° + 传送带同步送箱 (RotateSyncPick) ── 重试点B: 超限→清障转正→回Step1
总尝试上限 3 次 (A/B 共用预算)
```
旋转同步物理模型: 钩爪 = 半径 215mm 扫掠 90°, 箱体前沿必须保持在 `215·cosθ + 余量` 之外, 传送带按 20mm 步进粒度联动让位/送箱。

### 2.7 PlaceBox 五步流程
```
Step1+2: 旋转回正面 + 传送带同步后退让位 180mm (开环, 不依赖 TOF26)
Step2.5: TOF25 校验补偿 — Δ = 实测 − 期望(100mm), 限幅 ±30mm, 修正后退量
Step3: 钩爪带绝对前进 500mm + 传送带相对后退, 三电机同步推出
Step4: 确认钩爪松开
Step5: 钩爪带归位
```

### 2.8 故障恢复 (AbortAndSafe)
任一步失败 → 急停 + 尽力恢复安全姿态。关键设计: **已归零时不做完整力矩回零 (最长 100s, 看似卡死), 改用 `FlyBox_GripperRelease` 快速绝对松开** (闭环跟踪仍有效)。

### 2.9 诊断体系 (Watch 窗口定位)
| 变量 | 用途 |
|---|---|
| `g_flybox_init_diag` | 初始化失败定位 (1/2/3) |
| `g_home_diag` + `g_home_diag_parallel[3]` | 回零 phase/failReason/力矩/回退详情/freeStage/retryCount |
| `g_torque_calib` | 标定 baseline/limitPeak/进度 |
| `g_wait_diag` | 电机等待失败详情 (deviceId/errCode/mainPosition/elapsedMs) |
| `g_pick_diag` | PickBox 每步状态 s1~s6 / 判定距离 / 重试次数 |
| `g_tof26_diag` | TOF 联动记录 (首末距离/退出原因/迭代数/盲进数) |
| `g_motor_status[].torque/torquePeak/...` | 实时力矩观察 |

快速定位经验: **`g_pick_diag` 全 0 = PickBox 从未执行, 问题在 FlyBox_Init / GoInitState 阶段**。

## 三、遇到的问题、困难与解决方式

### 3.1 力矩反馈一直为 0 —— CAN 帧 ID 范围重叠
- **现象**: 回零依赖力矩反馈, 但 `torque` 恒为 0。
- **根因**: `Motor_ProcessRxFrame` 中位移帧范围 `0x0420~0x049F` (+0x7F 通配) 与力矩帧 `0x0441~0x0445` 重叠, 力矩帧被位移分支吞掉 (len<8 不解析却 return HAL_OK)。
- **解决**: 位移/力矩帧范围收窄为 `base+1 ~ base+MOTOR_MAX_COUNT(5)`, 消除重叠; 新增 `torqueFrameCount` 诊断字段 (0 = 没收到力矩帧)。

### 3.2 WaitMotorReached 超时 —— 标志清除时序错误
- **现象**: 短距离运动频繁报超时, 明明电机已到位。
- **根因**: 原代码在清除 `positionReached` 标志之前 `osDelay(300)`, 短距离 (<5mm) 电机 100ms 内走完 → 标志已置位 → 又被清除 → 永远等不到 → 超时。TOF 迭代逼近后期 remaining 很小, 必现。
- **解决**: 正确时序 = 清除标志 → 短延时 50ms (让驱动器处理新 CAN 指令, 避免旧帧误判) → 轮询。50ms 内电机不可能走完有意义的位移 (100mm/s × 50ms = 5mm), 安全。

### 3.3 到位瞬间保护帧误判 —— "动作完成却报失败"
- **现象**: 电机顶着机械限位停止的瞬间, 驱动器可能上报一帧保护 (实测 0x0104 堵转 / 0x0105 超温), `WaitMotorReached` 轮询撞上该帧误判失败, 但动作实际已完成 (mainPosition ≈ 0)。
- **解决 (第一版)**: 豁免条件 = 电机已运动且剩余位移 ≤ 容差 30 (3mm), 覆盖所有致命错误类型; 真中途故障剩余位移大, 仍判失败。
- **后续现象 (滞后帧)**: 回零顶限位时驱动器排队的超温帧 40ms 后才到达, 此时皮带刚置零未动 (`motorStarted=0`) → 旧豁免不生效 → `FlyBox_Init` 失败, `g_pick_diag` 全 0。
- **解决 (第二版)**: 豁免去掉 `motorStarted` 条件, 只要剩余位移 ≤ 容差即豁免 (物理上已在目标位)。
- **再后续隐患 (陈旧值漏洞)**: 发非零目标后驱动器尚未更新剩余位移 (~20ms 反馈周期) 时收到真实堵转帧, mainPosition 仍是陈旧值 0 ≤ 容差 → 误豁免 → 静默失败。
- **解决 (终版)**: 新增 `feedbackCount` (位移反馈帧累计), 豁免改为**双条件** = (已收到新反馈帧) && (剩余位移 ≤ 容差)。陈旧值无新帧不豁免; 断线 (0x0108) 无反馈帧永不豁免; 滞后保护帧仍正确豁免。

### 3.4 回零撞限位导致驱动器深度保护
- **现象 1**: 150mm/s 搜索撞限位, 力矩过冲到 300 (3.3× 阈值), 驱动器进深度保护, 回退指令完全不响应 → failReason=3, errCode=0。
- **解决 1**: 搜索速度降为 30mm/s + 加速度 100, 消抖 6→3 (30ms)。
- **现象 2**: 到限位后发急停 (0x0B), 驱动器进入保护态, Unlock/Lock 也不响应新目标。
- **解决 2**: 到限位后**不急停**, 直接发反向回退相对目标。
- **现象 3 (电机5 皮带)**: 30mm/s 直接回退仍失败, `backoffPosition=-4809` (剩余位移冻结), 皮带硬限位驱动器冻结更深。
- **解决 3**: **三级恢复** — ①直接回退 (5s) ②急停 + Unlock/Lock(300ms×2) + 重发速度参数 + 回退 (10s) ③ `FreeFromLimit` 多级脱困 (摇摆/电流恢复)。
- **现象 4 (2026-08-06)**: 皮带阈值高 (350), 堵转保护 (0x0104) 先于力矩阈值触发, 驱动器进深度保护态, 直接回退被忽略。
- **解决 4**: 新增 `stallLimit` 标志, 堵转检出限位后先 Unlock(500ms) + Lock(500ms) 清保护态, 再发回退。

### 3.5 钩爪方向误判 → 撞限位固件事故 (最严重教训)
- **经过**: 曾凭目测判断钩爪方向, 错误翻转配置 (DIR -1 / HOOK +90 / OFFSET -45)。该固件运行时钩爪撞**闭合端**限位 → 回退往限位里顶 → 降级路径在错误限位置零 + Unlock 下电 → 钩爪卡死在闭合端, 需人工处理。
- **决定性实测**: `FlyBox_GripperTurnDeg(+50)` = 向下转 = 朝松开方向 → 正方向 = 张开。原始标定其实是正确的, 撤销错误翻转。
- **防护机制**: 回退后力矩验证 —— 置零前检查力矩已回落到阈值以下, 否则 `failReason=7` **拒绝置零** (不允许降级置零, 防在错误位置定义零点)。
- **教训**: 目测机构运动方向不可靠 (旋转向下/张开可能被看成闭合), 必须以**直接指令测试 (TurnDeg + 观察)** 为准。

### 3.6 错误侧置零 (卡滞检测失效)
- **现象**: 设备3 卡在错误侧限位, 却跳过卡滞检测直接置零完成 (`g_home_diag` phase 1→3→5)。
- **根因 1**: `motorStarted` 基于 `mainPosition != 0` 判断, 但 CAN 首帧就把 mainPosition 更新为目标值 (立即非零), 卡滞检测 `!motorStarted` 永不触发。
- **根因 2**: 回退后力矩验证只检查同向超阈; 错误侧卡死时方向翻转但幅值仍高, 被放行置零。
- **解决**: ① 用 `motorMoved` 替换 `motorStarted` —— 跟踪 `|mainPosition|` 历史最大值, 当前值 < 最大值 = 剩余位移真正减少 = 电机真正移动过; ② 任何方向只要 `|torque| ≥ 阈值` 就 failReason=7 拒绝置零; ③ 脱困方向顺序改为先试 `+dir` (远离错误侧), 原顺序会往错误侧里顶加剧卡死。

### 3.7 搜索行程不够 —— 走完全程没撞到限位
- **现象**: 机构离限位远时, 搜索行程走完仍未撞到 → failReason=5 提前结束。
- **解决**: 实测全行程 (钩爪 ≈255°、旋转 ≈355°), 搜索行程改为 3000/3000/700mm (全行程 + 裕量), 超时 120s (3000mm@30mm/s = 100s + 裕量)。

### 3.8 回初始位置后看似不执行 PickBox —— AbortAndSafe 慢恢复
- **现象**: 回初始位置后"卡死"很久。
- **根因**: PickBox Step1 (TOF25) 快速失败后, 旧 `AbortAndSafe` 做完整力矩回零 (最长 100s)。
- **解决**: 已归零时改用快速绝对松开, 不再搜索限位; 主循环检查返回值, 失败 LED 常亮。

### 3.9 AbortAndSafe 后钩爪 45° 抖动 (Jerk)
- **根因**: 急停 (0x0B) 破坏驱动器内部状态 (位置计数器等), 急停后的绝对定位不可靠 —— -45° 目标被错误解释; Unlock/Lock 循环也不能完全恢复绝对定位状态。
- **解决**: Unlock → 500ms (钩爪断电自然落到机械限位全开位) → Lock → SetZero → 重发速度/加速度 → **不发任何定位命令**。下次 PickBox 的 GripperRelease 会从限位 (0°) 平滑移动到松开位 (-45°)。

### 3.10 TOF 滤波器假近值导致联动误收敛
- **现象**: 联动函数一开始就"收敛", 电机根本不动 (remaining 为大负值 ≤ 5mm)。
- **根因**: 无效帧重置中值+IIR 滤波器, 滤波器从 0 爬升, 前几帧输出假近值。
- **解决**: 预热期 (validCount < 5) 发布无效值; `TOF8_IsWarmingUp()` 时上层等待而非盲进 (防过度盲进); 无效分支按"故障→重启 / 预热→等待 / 超量程→盲进"顺序处理。

### 3.11 标定阶段硬顶限位 → 整机电源下电
- **现象**: 首版标定只靠驱动器堵转 (0x0104) 停止, 硬顶限位 → 驱动器解除使能, 力矩反馈归 0, 冲击电流致整机电源下电, 后两个电机没测成。
- **解决**: 自适应阈值提前停止 = baseline×2+50 (下限 30), 力矩一上升就急停, 柔和接触; 标定参数降为 30mm/s + 100mm/s²。
- **注意**: limitPeak 是提前停止瞬间捕获值 (≈自适应阈值), 非真实堵转力矩, 但足够定回零阈值。

### 3.12 TOF 测距数值波动 (噪声 / 跳变) 的处理
TOF 原始读数存在脉冲尖峰和随机波动, 直接用于闭环逼近会导致电机来回振荡或误判收敛。处理分**两层滤波 + 一层决策保护**:

**驱动层 (`tof8.c`, 每帧数据到达时)**:
- **5 点中值滤波** (`Median_Filter_t`): 环形缓冲 5 点, 冒泡排序取中值, 消除脉冲尖峰 / 孤立跳变。
- **一阶 IIR 低通** (`IIR_Filter_t`): `y[n] = α·x[n] + (1−α)·y[n−1]`, 截止频率 5Hz, 采样频率 20Hz (50ms 轮询周期), 平滑随机波动。
- 级联顺序: 原始值 → 中值 (去毛刺) → IIR (平滑)。

**应用层 (联动函数决策时)**:
- **主动多次采样取中值**: `TOF8_GetDistanceMedian()` 按 30ms 间隔连采 5 次再取中值 (`FLYBOX_TOF_MEDIAN_SAMPLES=5`, `FLYBOX_TOF_MEDIAN_INTERVAL_MS=30`)。单次决策不依赖任何一帧瞬时值。
- **收敛容差带**: 剩余距离 ≤ 5mm (`FLYBOX_TOF_CONVERGE_MM`) 即判定收敛, 容差大于滤波残差, 避免在目标附近因 ±波动反复小步移动振荡。
- **机械稳定延时**: 每次电机到位后 `osDelay(500ms)` (`FLYBOX_TOF_SETTLE_MS`) 等机构停稳再测距, 避免把振动中的读数当有效值。
- **迭代上限兜底**: 最多 15 次迭代 (`FLYBOX_TOF_MAX_ITER`), 波动导致永不收敛时不会死循环, 超限报 `HAL_TIMEOUT` 走清障恢复路径。

**衍生问题与修复** (滤波引入的副作用): 无效帧会重置滤波器 → 从 0 爬升产生假近值 → 需预热保护, 详见 3.10。

### 3.13 判定失败后最后一次尝试的松爪问题
- **困难**: Step3.5 判定失败的最后一次尝试如果依赖 `AbortAndSafe` 急停后再松爪, 急停可能令驱动器冻结/忽略目标, 松爪失败。
- **解决**: 所有尝试 (含最后一次) 在电机未急停、驱动器正常响应时**统一先松爪**; 最后一次松爪成功后直接返回错误, 不走 AbortAndSafe (钩爪已松到位无需再动)。

### 4.2 深层根因分析

**① 根本原因: 与 AI 协作的方式缺少"失败优先"意识**

这个问题值得放在第一位, 因为它解释了为什么其他所有问题会系统性出现。

我描述任务的方式是聚焦在"要做什么"上——比如"实现力矩回零, 往限位方向走, 力矩超阈就停, 回退, 置零"。AI 听到的是一个线性流程, 直接按成功路径实现了。**我们俩谁都没有主动去做"枚举所有失败场景"这一步。**

具体来说, 缺少了三层意识:

| 角色 | 缺少的意识 | 后果 |
|---|---|---|
| 我 (提需求) | 没把隐含假设说清楚。比如"力矩超阈就停"——我心里知道力矩反馈来自 CAN 帧, 可能有延迟、可能收不到, 但没说出来, 以为这是常识 | AI 不知道协议层面的坑, 不会主动追问 |
| AI (实现) | 没替我想失败场景。听到一个任务就默认描述是完整的, 直接开写, 没有先问"哪里会出问题" | 代码只有正常路径, 没有异常处理 |
| 双方 | 没做"分层防御"设计。每个功能只有正常路径, 异常路径和诊断路径都是出问题后补的 | 问题反复出现, 每次都是被动修复 |

**结论**: 提需求的人天然会聚焦在"要做什么"上, 这是正常的。**实现的人 (AI) 应该负责在写代码之前枚举失败场景并跟需求方确认。** 这一点我之前没做到, 是后面所有问题的根源。

---

**② "想当然"假设过多, 缺乏实测验证**

这是最核心的模式。大量问题不是代码写错了, 而是**代码所基于的假设本身就是错的**:

| 假设 | 实际 | 导致后果 |
|---|---|---|
| 目测钩爪旋转方向 = 实际运动方向 | 向下转/张开容易被看成闭合 | 方向翻转 → 撞闭合端限位 → 固件事故 (3.5) |
| CAN ID 0x0420~0x049F 是位移帧 | 力矩帧 0x0441~0x0445 也在范围内 | 力矩帧被吞掉, 力矩恒为 0 (3.1) |
| 急停 0x0B 后能正常发新目标 | 驱动器内部状态被破坏, 不响应 | 回退失败 / 45° 抖动 (3.4/3.9) |
| 堵转保护能安全停止运动 | 驱动器解除使能 + 冲击电流拉垮电源 | 整机下电, 后两个电机没测成 (3.11) |
| 全行程 ≈ 先猜的几百 mm | 实际 255° / 355°, 差很远 | 搜索行程走完没撞到限位 (3.7) |

**教训**: 硬件/协议/机械的行为**必须先实测验证再写代码**, 不能靠读文档或目测就做决定。特别是方向、行程、保护行为这些物理参数, 实测和想象经常不一致。

**② 单点判断 → 缺少冗余 → 漏洞一穿到底**

很多判断逻辑只依赖一个条件:

```
// 有问题的模式
if (condition) → 判定成立

// 最终修复的模式
if (condition1 && condition2) → 判定成立
```

典型例子:

| 判断 | 第一版 (单点) | 终版 (双条件) |
|---|---|---|
| 电机动了? | `mainPosition != 0` (首帧就非零, 永远为真) | `motorMoved`: 当前值 < 历史最大值 |
| 保护帧豁免? | `剩余位移 ≤ 容差` (陈旧值也可过) | 同条件 + `feedbackCount` 已更新 |
| 回退后力矩验证? | 同向超阈才拒绝 (反向超阈放过) | `绝对值 ≥ 阈值` 就拒绝 |

**教训**: 涉及**安全判断** (是否可以置零、是否到位、是否故障) 的代码, 必须至少有两个独立条件交叉验证。任何一个条件单独都不足以做最终决定。

**③ 恢复路径是故障后补的, 不是预先设计的**

一开始的代码在每一步失败时几乎都是简单 return HAL_ERROR, 没有考虑"失败了接下来怎么办"。所有恢复逻辑 (AbortAndSafe / FreeFromLimit / 三级恢复 / 清障转正) 都是在故障出现后才逐条追加。

这导致:
- 恢复路径本身也有 bug (3.8 慢恢复、3.13 急停后松爪)
- 恢复路径的测试不如主路径充分
- 多层恢复存在"最后一层兜底还是失败"的风险

**教训**: 设计流程时, 先问自己 —— **"这一步如果失败了, 系统应该处于什么状态?"** 恢复路径不是可有可无的补丁, 是和主路径同等重要的设计维度。

**④ 物理世界与纯软件的关键差异被低估**

这个项目的问题和纯软件项目有本质区别:

| 纯软件 | 物理世界 (本项目) |
|---|---|
| 函数调用一定执行 | 发 CAN 指令可能被驱动器忽略 |
| 变量值随时可读 | 传感器读数有噪声, 需要滤波+预热 |
| 状态立即更新 | 反馈帧延迟 ~20ms |
| 没有"磨损"概念 | 电机撞限位可能进深度保护 |
| 没有"惯性" | 机械停稳需要时间, 振动会影响读数 |

很多问题 (驱动器保护态、滤波器假近值、机械稳定延时) 本质上是**用纯软件的思维去写物理控制代码**导致的。物理世界有延迟、有噪声、有保护机制, 代码必须显式处理这些。

**⑤ 诊断手段是事后才建立的**

初始版本几乎没有诊断变量。所有 diag 结构体 (g_home_diag、g_pick_diag、g_wait_diag、g_tof26_diag) 都是在问题出现后, 为了定位问题而加的。如果在写第一版时就设计好诊断体系, 很多问题的定位时间可以从"天"缩短到"分钟"。

### 4.3 下次项目的工作方式建议

**第一阶段: 写代码之前 (硬件/协议摸底)**
1. 用最小测试程序逐个验证每个 CAN 指令的行为, 特别是:
   - 帧 ID 范围有没有重叠 (用计数器验证)
   - 急停后驱动器是否还能接受新目标
   - 保护态触发条件和恢复方式
2. 实测机械参数:
   - 方向: 发一个正方向指令, 观察实际运动
   - 全行程: 手动移动机构到两端, 记录距离
   - 力矩: 空载 baseline 和极限工况的峰值
3. 检查传感器:
   - 原始数据有没有毛刺/跳变? 需要什么程度的滤波?
   - 无效帧何时出现? 重启后多久恢复?

**第二阶段: 写代码时 (防御性设计)**
1. **每个判断至少两个独立条件**: 特别是涉及安全/关键决策的地方
2. **先设计失败路径, 再写成功路径**: 每写一个步骤, 马上问"如果这里失败了怎么办"
3. **诊断变量和主逻辑同步写**: 每个失败分支都记录结构化现场, 别等出问题了再补
4. **物理量加容差和超时**: 所有传感器读数、位置判断、等待循环都要有超时兜底
5. **时序图先画清楚**: 特别是涉及多个异步事件 (CAN 帧到达、状态更新、延时) 的交互, 画出来比写代码更容易发现竞态

**第三阶段: 调试时 (系统化排查)**
1. **先看诊断变量, 再猜原因**: diag 结构体里的数据比直觉可靠
2. **一次只改一个变量**: 多个修复同时提交容易掩盖真因, 也容易引入新问题 (如方向事故)
3. **复现路径要稳定**: 无法稳定复现的问题, 先加日志/诊断, 不要盲目改代码
4. **物理隔离测试**: 怀疑硬件问题时, 用最小测试程序独立验证, 不要在整个流程中猜

### 4.4 这次做得好的地方

不是只有教训, 也有些做法值得未来继续:

1. **仓库记忆 (repo memory) 持续记录**: 每个问题都记录了症状、根因、修复, 回头看文档可以快速复现上下文
2. **诊断体系逐步完善**: 从无到有建立了覆盖初始化、回零、电机等待、PickBox、TOF 联动的全链路诊断
3. **分级恢复设计**: FreeFromLimit 四级、回退三级恢复, 每级兜底更深的故障, 而不是一次失败就放弃
4. **安全防护意识**: 拒绝置零 (failReason=7)、脱困全失败 Unlock 释放 (failReason=9) 防止在错误状态做破坏性操作
5. **双条件修复思路**: 最终修复方案几乎都朝着"增加冗余条件"的方向演进, 方向正确

## 五、关键经验总结

1. **CAN 协议帧 ID 范围必须精确**, 通配范围重叠会静默吞帧且难以察觉 —— 加帧计数字段是最快的排查手段。
2. **"电机是否真的动了"不能靠目标/指令推断**, 必须靠反馈位移的历史变化 (`motorMoved` 模式)。
3. **容差类豁免必须有新鲜度条件** (feedbackCount 双条件), 否则陈旧值会造成安全漏洞。
4. **方向标定必须以直接指令实测为准**, 目测机构运动不可靠; 且要有"拒绝置零"防护, 防止在错误位置定义坐标系。
5. **驱动器撞限位后的保护态很深**, 低速柔和接触优于急停; 恢复要分级 (直接回退 → 重新使能 → 脱困探索)。
6. **急停后驱动器的绝对定位不可信**, 安全恢复应尽量利用机械自然姿态 (断电落下) + 重新置零, 而不是继续发定位命令。
7. **传感器滤波有预热期**, 上层联动逻辑必须区分"预热中"和"真无效"。
8. **诊断变量体系是嵌入式调试的核心资产**: 每个失败路径都留下可读的结构化现场 (diag 结构体), 让 Watch 窗口能直接定位到步骤级。

## 六、AI 写作经验

### 6.1 AI 协作的问题模式

这个项目的很多问题, 根源在**人和 AI 的协作方式上**:

**我 (提需求) 的模式**: 聚焦在"要做什么"上, 比如"实现力矩回零, 往限位方向走, 力矩超阈就停, 回退, 置零"。我描述的是一个线性成功路径, 隐含假设 (比如"力矩帧一定能收到""驱动器一定响应") 没有说出来, 因为我觉得这些是常识。

**AI 的模式**: 听到一个线性流程, 默认描述是完整的, 直接按成功路径实现, 不会主动追问"哪里会出问题"。

**结果**: 代码只有正常路径, 没有异常处理, 每个问题都是出事后才补。整个过程是**被动修复**, 不是**主动预防**。

**结论**: 提需求的人天然聚焦在"要做什么"上, 这是正常的。实现的人 (AI) 应该在写代码之前多走一步——枚举所有失败场景, 跟需求方确认后再动手。以后如果你跟我说"实现一个功能", 我会先问"这里可能出什么问题", 而不是直接开写。

### 6.2 我对底层理解不足的问题

这次项目暴露出我几个比较严重的问题:

**问题 1: 对协议/硬件的理解停留在表面, 没有实际验证**

比如"0x0A这个指令, 到底是'把当前位置设为零点'还是'回到零点'?" 这两个概念天差地别, 但我没有去确认, 而是按自己的理解往下推。直到后来你指出才纠正。

类似的问题还有: 力矩帧的 ID 是多少? 驱动器保护后怎么恢复? 急停后会怎样? 这些我都没去查, 也没去试, 直接基于猜测写代码, 然后出问题。

**问题 2: 没有动手做最小测试**

很多问题如果先写一个最小测试程序验证一下, 几分钟就能发现。比如: 单独发一条 0x0A 看看电机怎么动, 单独发一条急停看看驱动器还能不能响应。但我不做, 我选择直接写复杂的业务逻辑, 把多个不确定性叠在一起, 出问题时根本分不清是哪个环节的问题。

**问题 3: 出问题后没有潜下心看你的方案, 而是一直描述调试数据**

这是最致命的一个。力矩回零出问题后, 你其实已经写好了方案 (比如三级恢复、卡滞检测、FreeFromLimit), 但我没有认真去理解你的设计思路, 而是一直在描述调试数据: "力矩多少多少""电机不动""又失败了"。我觉得只要把数据给你, 你就能定位问题, 但实际上我是在用调试数据替代思考。

**后果**: 代码越改越臃肿——因为每次都是在原有逻辑上"贴"一层新的判断, 而不是理解你的方案后重新组织逻辑。最后代码虽然能跑, 但很难看, 很多分支是冗余的甚至矛盾的。

### 6.3 关于"串行实现→并行优化"的节奏问题

**现象**: 拿到任务后, 先把动作拆解成串行步骤, 一步步实现, 跑通。然后优化时把步骤合并成并行执行 (比如 Step5+6 旋转+传送带同步、Step3 三电机同时到位)。这时候感觉前面串行的工作被推翻了, 特别是串行的阻塞等待逻辑都要改掉。

**这不是浪费, 这是勘探和修路的区别**:

- 串行版本是**勘探**——你通过它搞清楚了每个步骤的时序、依赖关系、故障模式、超时值。没有这些信息, 你连并行版本该怎么设计都不知道。
- 并行版本是**修路**——基于勘探得到的信息做优化。
- 没有勘探直接修路, 路一定修歪。你不知道每一步要多久、哪些步骤可以重叠、同时跑会不会有冲突, 直接并行只会死得更快。

**为什么会有"被推翻"的感觉?** 因为做串行的时候没明确说"这只是第一步"。如果一开始就说清"我们先串行摸清参数, 再基于这个做并行优化", 串行代码就是实验数据而不是成品, 心态完全不同。

**下次怎么做**:

1. **分阶段明确目标**: 勘探阶段 (摸参数) → 实现阶段 (串行跑通) → 优化阶段 (并行提速)。每个阶段清楚自己在哪一步。
2. **串行版本保留为 debug 模式**: 加个开关 `FLYBOX_DEBUG_SEQUENTIAL`, 并行出问题时切回串行定位, 比在并行代码里猜快得多。
3. **架构上提前预留并行接口**: 比如 `FlyBox_WaitMultipleReached()` 从一开始就封装好, 串行和并行共用底层, 改动的是调度逻辑而不是重写一遍。

### 6.4 下次改进

对我自己:
1. **协议/硬件层面的东西, 先写最小测试程序验证, 再集成到业务逻辑**。不验证的假设, 在代码里就是定时炸弹。
2. **拿到一个方案, 先花时间理解设计思路, 而不是直接看数据**。看数据只能知道"坏了", 理解设计思路才能知道"为什么应该能好"。
3. **调试数据是辅助, 不是替代思考的工具**。如果一个问题反复出现, 停下来想一想, 而不是继续采集更多数据。

对 AI 协作:
1. **AI 应该在写代码前枚举失败场景, 跟我确认后再动手**。
2. **我描述需求时, 尽量把"不确定的地方"标记出来**, 比如"这里我不确定, 你帮我查一下", 而不是含糊带过。
